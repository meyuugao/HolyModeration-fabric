Работаю в 3 стадии, **между стадиями — контрольная точка** (сборка + твой прогон). Каждая стадия оставляет мод рабочим.

## СТАДИЯ 1 — Бэкенд начисто + коннект с модом + Telegram-кнопки

### Формат данных (новый, чистый)
Инвертирую whitelist/blacklist в **`{hwid: nickname}`** (ключ — fingerprint, значение — владелец). Это естественнее для OR-логики бана и для кнопок TG (каждый fingerprint добавляется отдельно). Существующие 5 записей пересобирать не нужно — старые raw-UUID больше не валидны (новые хеши SHA-256), whitelist стартует пустым; модераторы пере-одобряются через кнопки при следующем заходе (ты это и хотел — «перестроим систему вместе»).

### Бэкенд: `backend/www/` (Flask, WSGI — `application = app`)

**Новые/переписанные файлы:**
- **`store.py`** — потокобезопасное (threading.Lock) чтение/запись JSON `{hwid: nickname}`. Методы: `list_whitelist()`, `list_blacklist()`, `add_whitelist(hwid, nick)`, `remove_whitelist(hwid)`, `add_blacklist(...)`, `remove_blacklist(...)`, `is_in_whitelist(hwid)`, `is_in_blacklist(hwid)`. Атомарная запись через temp+rename.
- **`telegram.py`** — бот: (а) `notify_launch(username, hwids)` — шлёт сообщение с inline-клавиатурой (см. ниже); (б) `handle_callback(callback)` — обрабатывает нажатие; (в) `set_webhook(url)` — однократная регистрация.
- **`__init__.py`** — Flask-роуты:
  - `POST /api/launch` — читает JSON-тело `{username, hwids:[...]}` (НЕ заголовки — надёжнее для списка), вызывает `telegram.notify_launch`, отвечает `{status:ok}`.
  - `GET /whitelist`, `GET /blacklist` — отдают новый формат `{hwid: nickname}`.
  - `POST /tg/webhook` — принимает Update от Telegram, диспетчирует в `telegram.handle_callback`.
  - `GET /tg/setup` — guarded by `ADMIN_TG_ID`, однократно вызывает `set_webhook(WEBHOOK_URL)`.
  - `GET /viewer` — без изменений.
  - Корень `/` — healthcheck.

**Env (в alwaysdata `.env`):** `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `ADMIN_TG_ID`, `WEBHOOK_URL` (=`https://holymoderation.alwaysdata.net/tg/webhook`).

### Telegram-кнопки: дизайн под «много fingerprint'ов сразу»
При заходе бот шлёт **одно** сообщение:
```
🎮 Заход на сервер
Ник: <username>
⏱ <время>

🔐 Fingerprints (нажмите, чтобы управлять):
```
Под сообщением — **inline-клавиатура**: по одной строке на каждый fingerprint (до 5). Каждая строка:
- слева короткая подпись источника (`[mb]`, `[bb]`, `[cpu]`, `[disk]`, `[nic]`) + первые 8 символов хеша (чтобы отличать);
- справа кнопки: `[+ ВЛ]` `[+ ЧС]`.

Если fingerprint уже в ВЛ/ЧС — соответствующая кнопка заменяется на `[✓ в ВЛ]`/`[− ВЛ]` (удалить).

**callback_data** короткий: `wl|<launchId>|<idx>` / `bl|<launchId>|<idx>` (launchId — инкрементный счётчик, idx — индекс fingerprint в этом launchе). TG-лимит 64 байта — `'wl|1234567|4'` = 13 байт, запас огромный. Сервер хранит `pending_launches[launchId] = {username, hwids:[...], ts}` в памяти (in-memory dict; при рестарте старые кнопки отвечают «устарело» — это нормально, кнопки сиюминутные).

**Авторизация:** `handle_callback` проверяет `callback.from.id == ADMIN_TG_ID`; иначе `answerCallbackQuery("нет прав")`. Защита = один админ.

### Мод: правки (минимум, локализованы)
- **`NetService.sendLaunchData`** — переключить с заголовков на **JSON-тело** `{username, hwids}` (`setDoOutput(true)`, `Content-Type: application/json`). Убрать bridge-заголовок `hwid`.
- **`NetService.getListAsync`** (единственное место парсинга JSON) — сменить `TypeToken<Map<String,List<String>>>` на `Map<String,String>` и развернуть key/value при flatten: `new SimpleEntry<>(entry.getValue(), entry.getKey())` → внутренний контракт `SimpleEntry(nickname, hwid)` сохранён.
- **`ModValidationService`/`UserValidationService`** — **не трогать** (они работают с нормализованным списком, формат-агностичны).
- Убрать мёртвый `HwidService.getHwid()` (legacy single), оставить только `getHwidsView()`.

### Контрольная точка стадии 1
- Деплой бэкенда → `curl POST /api/launch` с тестовым JSON → в TG приходит сообщение с 5 кнопками × 2 → нажатие `[+ ЧС]` добавляет fingerprint в `blacklist.json`, приходит подтверждение, `GET /blacklist` показывает его.
- В моде: заход тестера → сообщение в TG с кнопками; whitelist пуст → режим blacklist → если ничего не нажимать, тестер играет.
- `./gradlew build` зелёный.

## СТАДИЯ 2 — Незавершённый ввод в GUI (кнопки начинают работать)

Подтверждено разведкой: `action.execute()` нигде не вызывается, `MouseClickEvent` отсутствует, `MouseMixin` не пушит клик в EventBus. Делаю минимально-инвазивно по существующей архитектуре.

**Новые/изменяемые файлы (мод):**
1. **`event/impl/input/MouseClickEvent.java`** (новый) — `extends Event`, поля `button, x, y`.
2. **`mixin/MouseMixin.java`** — `onMouseButton` на `GLFW_PRESS` пушит `MouseClickEvent(button, x/guiScale, y/guiScale)` в EventBus (координаты уже scaled, как в существующем `onMouseScroll`).
3. **`InputService`** — альтернативно пушить из него (если координаты хранить); выберу вариант через mixin напрямую — меньше связанности.
4. **`ButtonDrawableElement`** — добавить `boolean handleClick(float parentW, float parentH, double mouseX, double mouseY)`: если `isMouseOver` и `enabled` → `action.execute()`, вернуть true. Hit-test уже есть в `Drawable`.
5. **`StatefulDrawableElement`/`DrawableElement`** — виртуальный `boolean handleClick(...)` с delegation к дочерним кнопкам (default: false).
6. **`GuiManagerModule`** — `@Subscribe onMouseClick(MouseClickEvent)`: если идёт drag — игнор; иначе итерация по drawable-модулям topmost-first, у первого попавшегося вызвать `handleClick`, остановиться.
7. **`ReportsParserDrawableElement`** — заменить 2 `System.out.println`-заглушки: «пропарсить» → реальный парсинг открытого контейнера жалоб (через `ScreenHandlerService`/чтение слотов); «клик по игроку» → выбор игрока. Плюс `clearButton` начнёт работать автоматически.

### Контрольная точка стадии 2
- В CONFIG-режиме (`MainGuiScreen`) кнопка реагирует на клик.
- `ReportsParserDrawableElement`: открыть сундук «Жалобы на игроков» → виден список → «пропарсить» заполняет кнопки → клик по игроку выбирает его → «очистить» сбрасывает.
